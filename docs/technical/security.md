# Безопасность

## Аутентификация

Аутентификация пользователей выполняется через JWT-токены (JSON Web Token).

При входе в систему (POST /auth/login) пользователь отправляет email и пароль. Пароль проверяется через bcrypt - сравнивается хэш из базы данных с хэшем введённого пароля. При успешной проверке бэкенд генерирует JWT-токен с временем жизни 24 часа и возвращает его в ответе.

Токен содержит в payload:
- sub - ID пользователя
- email - email пользователя
- role - роль пользователя (admin или operator)
- iat - время создания токена
- exp - время истечения токена

Токен подписывается секретным ключом JWT_SECRET из переменных окружения.

Фронтенд сохраняет токен в localStorage (если выбрано «Запомнить меня») или в sessionStorage. При каждом запросе токен добавляется в заголовок Authorization: Bearer {token}. При получении ответа 401 (Unauthorized) токен удаляется из хранилища и пользователь перенаправляется на страницу входа.

## Защита эндпоинтов

Все эндпоинты, кроме POST /auth/login, защищены JWT-гардом (AuthGuard('jwt')). При отсутствии или невалидности токена возвращается статус 401.

Дополнительно реализована защита по ролям (администратор и оператор) через RolesGuard.

Административные эндпоинты, доступные только роли admin:
- Все эндпоинты /admin/* (журнал действий, управление пользователями, системные настройки, резервное копирование, статистика, рассылка уведомлений)
- DELETE /document-types (создание типа доступно всем пользователям)
- DELETE /document-categories (создание категории доступно всем пользователям)
- POST и DELETE /departments (создание и архивация отделов)
- PATCH /departments/:id/restore (восстановление архивного отдела)
- DELETE /documents/route-templates (создание шаблонов доступно всем пользователям)
- PUT /settings/ai (изменение настроек AI-провайдера)
- GET /settings/export (экспорт данных)
- POST /settings/import (импорт данных)

Операторы имеют доступ ко всем операциям с документами (загрузка, проверка, маршрутизация, удаление, комментарии), уведомлениям, настройкам интерфейса и своих уведомлений, созданию справочников и шаблонов маршрутизации.

Операторы не могут:
- Удалять типы и категории документов
- Архивировать и восстанавливать отделы
- Удалять шаблоны маршрутизации
- Изменять настройки AI-провайдера
- Выполнять экспорт и импорт данных
- Просматривать журнал действий других пользователей
- Управлять пользователями и системными настройками

## Блокировка пользователей

Администратор может заблокировать любого пользователя через админ-панель. При блокировке:
- Все активные сессии пользователя завершаются
- Пользователь не может войти в систему (ошибка 403)
- Пользователь получает уведомление о блокировке

## Сессии

При каждом входе в систему создаётся запись в таблице user_sessions. Сессия содержит токен, IP-адрес, User-Agent браузера и время истечения (24 часа).

Пользователь может:
- просмотреть свои активные сессии (GET /security/sessions)
- завершить конкретную сессию (DELETE /security/sessions/:id)
- завершить все сессии кроме текущей (POST /security/logout-all)

Администратор может принудительно завершать сессии пользователей через админ-панель.

## Журналирование

Все входы в систему записываются в таблицу login_history с указанием IP-адреса и User-Agent браузера.

Все значимые действия пользователей записываются в таблицу audit_log через модуль AuditLog. Записи включают: ID пользователя, действие, ID документа (если применимо), детали в формате JSON, время.

Пользователь может просмотреть свою историю входов и журнал действий через интерфейс: Настройки - Безопасность.

Администратор может просматривать журнал действий всех пользователей через админ-панель (вкладка «Журнал») с фильтрацией по пользователю, действию и дате. Также доступна очистка старых записей журнала.

## Шифрование API-ключа AI

API-ключ AI-провайдера хранится в базе данных в зашифрованном виде. Используется алгоритм AES-256-CBC.

Ключ шифрования задаётся в переменной окружения ENCRYPTION_KEY (64 символа hex, 32 байта).

При сохранении ключ шифруется перед записью в базу данных. При использовании расшифровывается. В ответах API ключ возвращается в маскированном виде: первые и последние символы видны, остальные заменены на звёздочки.

При утере ENCRYPTION_KEY все сохранённые API-ключи становятся недоступны - потребуется ввести их заново.

## Хэширование паролей

Пароли пользователей хранятся в базе данных в виде хэша, сгенерированного через bcrypt с солью. Открытые пароли не хранятся и не логируются.

При смене пароля (POST /auth/change-password) требуется ввести старый пароль для подтверждения.

Администратор может сбросить пароль любого пользователя через админ-панель. При сбросе пароля все сессии пользователя завершаются, и он получает уведомление.

## Валидация входных данных

Все входящие данные проверяются через class-validator в DTO. Проверяются:
- формат email
- длина пароля (минимум 6 символов)
- обязательные поля
- допустимые значения (например, theme может быть только light или dark)
- числовые диапазоны (например, defaultPageLimit от 5 до 100)

При ошибке валидации возвращается статус 400 с описанием ошибки.

## Безопасность файлов

Загружаемые файлы проверяются:
- по расширению и MIME-типу (разрешённые форматы настраиваются администратором в системных настройках)
- по размеру (максимальный размер настраивается администратором, по умолчанию 50 МБ)

Файлы сохраняются в папку uploads/ с уникальными именами. Доступ к файлам осуществляется через API с проверкой JWT-токена.

## Системные настройки безопасности

Администратор может настраивать ограничения загрузки через админ-панель (вкладка «Система»):
- Максимальный размер файла (МБ)
- Максимальное количество файлов за одну загрузку
- Разрешённые форматы файлов

Эти настройки сохраняются в таблице system_settings и применяются при каждой загрузке документа. Пользователи видят актуальные ограничения на странице загрузки.
